# PZSDR P501 — Vivado + PetaLinux Board Support

A working Vivado 2024.1 / PetaLinux 2024.1 board support package for the
[Puzhi PZSDR P401/P501](https://www.puzhi.com) software-defined radio board
(Zynq UltraScale+ MPSoC, AD9361 2T2R transceiver). The vendor's own reference
design is derived from Xilinx's ZCU102 + Analog Devices' FMCOMMS2/3 reference
project, and — as documented below — a lot of that reference design's
assumptions about pin wiring, clocking, and peripheral addressing simply don't
match this board's real hardware. This repo is the result of tracking those
down one at a time against the real schematic and the official user manual.

## Status

| Peripheral | Status | Notes |
|---|---|---|
| UART console | ✅ Working | PS UART1 (`ttyPS1`), not UART0 |
| Root login | ✅ Working | password `root` — **change this before deploying** |
| AD9361 (SPI/RX/TX) | ✅ Working | SPI control, RX DMA, TX DDS, internal loopback all verified; RX capture ~220MB/s (coherent DMA) |
| USB (gadget mode) | ✅ Working | Composite USB gadget: native libiio (FunctionFS) + CDC-ECM network, PlutoSDR-style |
| USB (host mode) | ⚠️ Not in this build | `dr_mode` is a build-time choice — see below |
| Ethernet (RGMII, 1G) | ✅ Working | Realtek RTL8211F, confirmed 1Gbps link + real bidirectional traffic |
| SFP (10G) | ❌ Not implemented | Needs a full 10G MAC/PCS-PMA/GT subsystem — separate, larger undertaking |
| GPS, Mini DP, SSD, 40P expansion | ❌ Untouched | Inherited from the stock reference tree, not verified |
| PYNQ image | 🚧 Not started | Board bring-up is solid enough to begin; see Roadmap |

## Repository layout

```
hdl/                    Vivado 2024.1 project source
  P501_IIO.xpr           project file
  P501_IIO.srcs/          XDC constraints, block design (system.bd), IP references
  library/                vendored ADI open-source IP cores (axi_ad9361, axi_dmac, etc.)
  system_top.xsa          pre-built hardware handoff (bitstream + hw description)
  CLAUDE.md               notes on the Vivado project structure

petalinux/              PetaLinux 2024.1 project source
  project-spec/           the actual board customization (device tree, kernel config,
                           rootfs config, custom recipes) — this is the real source of truth
  meta-adi/               ADI's meta-adi-xilinx Yocto layer (2023_R2 branch), needed for
                           the AD9361 kernel driver stack and spi_engine support
```

Deliberately **not** included: Vivado's `.runs/`/`.gen/`/`.cache/` (regenerated
by synthesis), and PetaLinux's `build/`/`images/`/`components/` (regenerated
by `petalinux-build`, and tens of GB). Both tools fully reconstruct their
working state from what's checked in here.

## Building

### Hardware (Vivado 2024.1)

```bash
cd hdl
vivado P501_IIO.xpr
```

In the Tcl console, or via a batch script:
```tcl
reset_run synth_1
launch_runs synth_1 -jobs 4
wait_on_run synth_1
reset_run impl_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
open_run impl_1
write_hw_platform -fixed -include_bit -force system_top.xsa
```

On first open, Vivado may prompt about the custom IP repository path — point
it at `./library` if it doesn't resolve automatically.

### Linux (PetaLinux 2024.1)

```bash
petalinux-create -t project --template zynqMP -n p501_iio
# replace the skeleton's project-spec with this repo's:
rm -rf p501_iio/project-spec
cp -r petalinux/project-spec p501_iio/
cp -r petalinux/meta-adi p501_iio/
cd p501_iio
petalinux-config --get-hw-description=../hdl/system_top.xsa --silentconfig
```

**Important manual step**: `meta-adi` must be registered in
`build/conf/bblayers.conf` (this file is regenerated by `petalinux-config` and
isn't tracked here, so the layer reference doesn't persist automatically).
Add a line like:
```
BBLAYERS += "${TOPDIR}/../meta-adi/meta-adi-xilinx"
```
to `build/conf/bblayers.conf` before building.

```bash
petalinux-build
petalinux-package --boot --fsbl images/linux/zynqmp_fsbl.elf \
    --fpga images/linux/system.bit --u-boot images/linux/u-boot.elf \
    --pmufw images/linux/pmufw.elf --force
```

Copy `images/linux/BOOT.BIN`, `images/linux/image.ub`, and
`images/linux/boot.scr` to a FAT32-formatted SD card. Set the board's boot-mode
DIP switches to SD1 Card mode (M2=1, M1=0, M0=1) and power on.

## Root causes found and fixed

Every one of these followed the same pattern: the vendor's reference design
was adapted from Xilinx's ZCU102 + ADI's FMCOMMS2/3 project, and some pin,
clock, or peripheral-instance assumption from that donor design was never
corrected for this board's actual wiring.

- **UART RX dead**: the inherited device tree's `uart1-default` pinctrl group
  muxed MIO20/21 (the ZCU102's own UART1 pins) in addition to this board's
  real UART1 pins (MIO40/41), corrupting the shared RX line. Fixed by dropping
  the stale pinctrl reference entirely.

- **AD9361 wouldn't come up**: the vendor's XDC had all LVDS differential pair
  P/N assignments wrong (an automated PDF pin-extraction approach turned out
  to be unreliable for differential pairs specifically). Fixed using
  schematic-verified readings cross-checked against Vivado's own
  `DIFF_PAIR_PIN` property.

- **USB3 never enumerated**: the PS-GTR SerDes PHY block was left disabled,
  and its reference clocks were wired to an inherited `si5341` clock
  synthesizer chip that doesn't exist on this board (it lives on the FMC
  mezzanine the reference design assumes). Fixed by re-enabling the PHY and
  pointing its clocks at a `fixed-clock` matching the real on-board oscillator
  frequency recorded in Vivado's own PS8 config.

- **USB gadget mode (PlutoSDR-style)**: the board's Type-A USB3 port uses a
  USB3320C-EZK ULPI PHY with a VBUS power switch — genuinely dual-role
  capable in hardware (confirmed by the official user manual), but with no
  ID pin or role-switch wired, so host-vs-device is a `dr_mode` build-time
  choice, not a runtime toggle. `iiod -F <ffs_mountpoint>` serves libiio's
  native (non-IP) USB protocol via a FunctionFS gadget function — the same
  mechanism real Pluto hardware uses — composited alongside a CDC-ECM network
  function for ordinary IP/ssh access over the same cable.

- **Ethernet, in three parts**:
  1. The inherited device tree enables GEM3, but Vivado's PS8 config never
     actually enables GEM3 — it's GEM1 (EMIO-routed) that's real, confirmed
     against the official user manual's pin table.
  2. GEM1's RGMII *data* path was never wired in the Vivado block design at
     all — only the pin constraints existed, pointing at nothing. Fixed by
     instantiating and wiring `xilinx.com:ip:gmii_to_rgmii`.
  3. Even after that, MDIO stayed completely silent — confirmed via direct
     `devmem`-based register reads through the GEM's own MDIO controller
     (bypassing the Linux driver entirely) that the real Realtek RTL8211F PHY
     answers correctly, meaning the problem was software/bitstream, not
     hardware. Root cause: the `gmii_to_rgmii` IP's optional MDIO
     pass-through ports were silently breaking every transaction. Fixed by
     wiring MDIO directly from the PS to the physical pins, bypassing the
     bridge IP for that bus entirely (it still carries the GMII/RGMII *data*
     path, which was always fine).
  4. Link trained up fine but no actual traffic flowed until `phy-mode` was
     corrected from `rgmii-rxid` to `rgmii-id` — confirmed directly in the
     Realtek kernel driver source that `rgmii-rxid` explicitly disables TX
     clock-to-data delay compensation on the PHY, and this board's FPGA side
     doesn't add it either, corrupting every transmitted frame despite link
     training (a separate, simpler negotiation) succeeding.

- **AD9361 RX capture throughput capped at ~59MB/s regardless of sample rate**:
  the `axi_ad9361_adc_dma` master was wired to a plain, non-coherent PS HP
  port, so every CPU read of a capture buffer went through DRAM as uncached
  memory — the same ~59MB/s ceiling at 16MS/s and at 30.72MS/s, confirming a
  fixed CPU-read limit rather than anything USB/iiod/sample-rate dependent.
  Fixed by moving the RX DMA master to a coherent `S_AXI_HPC0_FPD` port (with
  its `AWUSER`/`ARUSER` sideband signals explicitly tied high — ZynqMP
  requires that bit asserted on HPC ports to actually get snooped/coherent
  transactions; left floating, it silently behaves exactly like a plain HP
  port) and adding `dma-coherent` to its device tree node. Measured result:
  ~220MB/s direct capture throughput, ~3.7x improvement. TX
  (`axi_ad9361_dac_dma`) stays on a non-coherent path by hardware necessity —
  the `axi_dmac` IP only implements coherent support for the memory-write
  direction (confirmed by its own probe failing with "Coherent DMA not
  supported in hardware" when tried on the TX/read side).

- **AD9361 `CTRL_IN`/`CTRL_OUT` GPIO pins misassigned**: `gpio_ctl[0]`,
  `[2]`, and `[3]` (FPGA outputs to the AD9361's `CTRL_IN0-3`) were instead
  wired to three of the AD9361's own `CTRL_OUT` pins — pins the AD9361
  itself drives as outputs, a direct driver-contention risk had the bus
  ever been toggled. Separately, 7 of the 8 `gpio_status` (`CTRL_OUT0-7`)
  bits were wrong: two were real `CTRL_OUT` pins at the wrong bit index,
  one sat on `AD9361_CLK_OUT` instead, and four matched no documented
  AD9361 pin in the official manual at all. Found by cross-checking every
  pin in the XDC against the vendor's own `AD9361 Communication Port`
  table; neither bus is referenced by the current device tree, so this was
  a dormant risk rather than an observed symptom. Fixed by remapping both
  buses 1:1 to the manual's `CTRL_IN0-3`/`CTRL_OUT0-7` pins.
